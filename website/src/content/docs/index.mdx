<section class="vp-home-sec" aria-labelledby="terminal">

<h2 id="terminal">Build it from the terminal</h2>

<p class="vp-home-p">People, AI agents and CI run the same commands.</p>

```bash prompt
vorpal init hello-world
vorpal prepare hello-world
vorpal build hello-world
$(vorpal build --path hello-world)/bin/hello-world
```

```text output title="Expected output of the last two commands"
<digest>
Hello, world!
```

<p class="vp-home-p">`prepare` pins every remote source in `Vorpal.lock` once; builds then run locked.</p>

<section class="vp-home-sec vp-home-how" aria-labelledby="scene">

<h2 id="scene">How the scene maps to Vorpal</h2>

<div class="vp-home-how-b">
<ul>
<li><b>Who:</b> people, AI agents and automations such as CI all use the same CLI. Agent daemon, registry and worker are separate services you can start on any machine with `vorpal system services start --services`; the CLI reaches each through `--agent`, `--registry` and `--worker`. <span class="vp-home-src">command.rs:98, 164-214; build.rs:816-820</span></li>
<li><b>Agent daemon</b> (a local service, not an AI agent): the build's config asks it to prepare sources. It checks them against `Vorpal.lock` and stops on a mismatch unless you pass `--unlock`, zeroes file times, hashes, packs (zstd) and pushes them to the registry only if they are missing. <span class="vp-home-src">sdk/rust context.rs:430-434; agent.rs:517-566, 700-731</span></li>
<li><b>Registry, anywhere:</b> the CLI takes `--registry` (or `vorpal config set registry`) and hands that address to the agent daemon, which checks and pushes sources there. A registry on a new machine starts with its own storage; this scene replays each stage as a fresh build. <span class="vp-home-src">command.rs:196-198; config.rs:96, 132; sdk/rust context.rs:414-420; agent.rs:448-454</span></li>
<li><b>Worker:</b> the CLI asks it to build each missing artifact and shows its logs. The worker pulls the sources from the registry, runs the steps, and pushes the archive back. Files never go from the CLI to the worker: the CLI checks its store, then the registry, and pulls archives straight from the registry. <span class="vp-home-src">build.rs:137, 233-262, 291; worker.rs:293-312, 968-982</span></li>
<li><b>Worker, anywhere:</b> `vorpal system services start` runs agent, registry and worker together by default, so one laptop can do it all; start a worker elsewhere with `--services worker` and point the CLI at it with `--worker` or `vorpal config set worker`. The CLI hands the worker its registry address, and the worker only builds artifacts whose target matches its own system, so the digest is the same on either machine. <span class="vp-home-src">command.rs:98, 212-214; config.rs:101, 137; build.rs:273-279; worker.rs:268-280, 1107-1121</span></li>
<li><b>Shared worker:</b> with sign-in on, any caller with `write` on the namespace (or a trusted service) can ask the worker to build; it locks each artifact while it builds. <span class="vp-home-src">worker.rs:1395-1407, 1090-1093</span></li>
<li><b>Other CLI users</b> pull from the registry the same way, with `vorpal build` or `vorpal run` for an alias. <span class="vp-home-src">run.rs:29-66, 94-130</span></li>
<li>Step secrets are sealed by the agent daemon (AES-256-GCM, RSA-OAEP key wrap) and opened only by the worker. <span class="vp-home-src">notary.rs:64-70; agent.rs:909-911; worker.rs:678-689</span></li>
</ul>
<ul>
<li><b>TLS:</b> services take `--tls` with keys from `vorpal system keys generate` (the generated certificate covers `localhost`; bring your own for a real host name). Clients use TLS for `https://` addresses and trust `ca.pem`. <span class="vp-home-src">start.rs:119-150; keys.rs:143; sdk/rust context.rs:727-745</span></li>
<li><b>OIDC:</b> with `--issuer`, the registry and worker reject calls without a valid token. Pulls need `read` on the namespace; builds need `write`. Client IDs in `--issuer-service-client-ids` are trusted services and skip namespace roles. <span class="vp-home-src">start.rs:220-238, 264-278; auth.rs:314-347, 481-520; registry.rs:236, 374, 467; worker.rs:1403-1407</span></li>
<li><b>Registry storage:</b> `--registry-backend local` or `s3`. The default address is a local socket, so share a registry by giving it a network address: `vorpal config set registry <address>`. <span class="vp-home-src">command.rs:101-105; config.rs:96, 132; sdk/rust artifact.rs:1008-1015</span></li>
<li><b>Sandboxed steps:</b> on Linux, the SDKs' shell steps run under Bubblewrap; on macOS they run in plain Bash for now <span class="vp-pln">Planned · <b>ENG-364</b></span>. <span class="vp-home-src">sdk/rust artifact/step.rs:59-85</span></li>
<li>Digests in the scene are computed in your browser from the Python SDK's own definitions (stand-ins: a remote source's digest is the SHA-256 of its URL; the app's is the SHA-256 of the line shown). Timings are illustrative. SBOM: Planned (ENG-373).</li>
</ul>
